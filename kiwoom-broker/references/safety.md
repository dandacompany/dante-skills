# 주문 안전 게이트

> 이 스킬은 조회를 편하게 해준다. **주문 안전은 스킬 바깥에서 설계해야 한다.**
> 래퍼의 `--confirm-order`는 사람이 실수로 주문을 내는 것을 막는 최소 장치일 뿐, 자동화의 안전장치가 아니다.

## 왜 필요한가

에이전트에게 주문 권한을 그대로 주면 다음이 실제로 일어난다.

- 프롬프트 인젝션이 "확인용 조회"를 "실제 매수"로 바꾼다
- 모델이 수량 단위·계좌·종목을 혼동한다
- 응답을 못 받은 주문을 재시도해 **중복 주문**이 된다
- 모의 프로필로 알고 있었는데 실전이었다
- 장 시작 트래픽에서 429를 반복 재시도해 상태가 더 불명확해진다

## 실행 모드

| 모드 | 무엇 | 기본값 |
| --- | --- | --- |
| `READ_ONLY` | 조회만 | ✅ 여기서 시작한다 |
| `DEMO` | 모의 계좌 주문 | 실습·검증 |
| `REAL` | 실계좌 주문 | 별도 승인 경로로만 |

**자동으로 승격되지 않는다.** 모드를 올리는 것은 사람의 명시적 행위여야 한다.

## 상태 머신

```text
DRAFT            판단이 주문 의도를 만든다
  → 정책 검사     한도·종목·시간 확인
  → 사전 조회     매수가능금액·현재가·장 세션
  → 사람 승인     ⏸ 여기서 멈춘다
  → 실행          승인된 내용 그대로 1회
  → 대사          주문 조회로 결과 확인
  → 체결 | 부분체결 | 미체결 | 거부 | UNKNOWN
```

### `UNKNOWN`은 실패가 아니다

주문을 보냈는데 응답을 못 받은 상황은 **성공도 실패도 아니다.** 나갔을 수도, 안 나갔을 수도 있다.

```text
주문 전송 → 응답 없음
  ❌ 재주문             중복 주문이 된다
  ✅ UNKNOWN 으로 기록  → 주문 목록 조회 → 실제 상태 확인 → 그때 판단
```

장부에 `unknown` 상태를 두고, **모르는 것을 모른다고 적는다.** 자동화에서 가장 위험한 건 실패가 아니라, 모르는 상태를 성공으로 적는 것이다.

## 지켜야 할 것

1. 기본 모드는 조회 전용. 실계좌는 자동으로 선택되지 않는다
2. 판단하는 프로필과 집행하는 프로필을 나눈다. **`.env`는 집행 프로필만 갖는다**
3. 주문은 구조화된 의도와 최신 사전 조회 없이 실행하지 않는다
4. **사람 승인은 그 주문 내용에 한정된 1회용이다.** 내용이 바뀌면 승인이 무효가 된다
5. 종목 허용 목록, 1회·1일 금액·수량 상한, 허용 시간을 코드로 강제한다
6. 같은 주문이 두 번 나가지 않도록 실행 단위에 고유 키를 붙이고 장부에 먼저 예약한다
7. 결과는 응답 한 번으로 확정하지 말고 주문 조회로 대사한다
8. 중단 스위치는 새 주문만 막고, 기존 주문의 조회·취소 경로는 살려둔다

## 승인 화면에 있어야 하는 것

사람이 승인 버튼을 누를 때 한 화면에 보여야 한다.

| 항목 | 왜 |
| --- | --- |
| **모의 / 실전 표시** | 가장 위에. 어느 계좌인지 착각하면 안 된다 |
| 종목명 + 코드 | 코드만 보면 헷갈린다 |
| 매수/매도 · 수량 · 단가 · 예상 총액 | 판단의 본체 |
| 현재가와 조회 시각 | 오래된 시세로 판단하고 있지 않은지 |
| 현재 평단 · 보유 수량 | 이 주문이 평단을 어떻게 바꾸는지 |
| 오늘 한도 소진분 | 한도 대비 어디까지 왔는지 |
| 판단 근거 한 줄 | 왜 이 주문인지 |
| 승인 만료 시각 | 언제까지 유효한지 |

여덟 줄이 많아 보이지만 **하나라도 빠지면 감으로 승인하게 된다.** 그러면 승인 게이트를 만든 이유가 사라진다.

## 오류별 대응

| 상황 | 조회 | 주문 |
| --- | --- | --- |
| 429 | 백오프 후 재시도 | **재시도하지 않는다.** 보고 후 정지 |
| 타임아웃 | 재시도 가능 | **`UNKNOWN`.** 주문 조회로 확인 |
| 인증 오류 | 토큰 1회 재발급 | 토큰 갱신 후 **사람에게 보고**, 자동 재실행 금지 |
| `return_code` 비0 | 사유 보고 | 사유 보고 후 정지 |

**주문에 재시도가 없는 것**이 이 계약의 핵심이다.

## 역할 분리 예시

| 역할 | 권한 |
| --- | --- |
| 분석 | 시세·지표 조회, 주문 의도 초안 (`.env` 접근 없음) |
| 검토 | 한도·근거 검증 |
| 사람 | 최종 승인·거부 |
| 집행 | 승인된 내용과 정확히 일치하는 주문 1회 (판단하지 않음) |
| 대사 | 주문·체결 상태 확인, 불일치 경보 |

여러 에이전트가 합의해도 **집행 권한이 생기지는 않는다.**
