# mail-campaign

시트 한 장과 `campaign.md` 한 장으로 수십~수백 통의 개인화 메일을 보낸다. 운영·거래 안내 메일(예약 확인, 일정 변경, 정산 안내)이 기본이고, 광고 메일은 광고성 판별을 통과한 뒤에만 보낸다.

역할 분담은 이렇다. **판단은 에이전트가 한다**: 문구 작성, 광고성 최종 판정, 답장 분류. **기계적인 일은 `scripts/mail_campaign.py` 가 한다**: 시트 읽기·쓰기, 검증, 렌더, 간격 발송, 기록. 발송·읽기는 전부 gws CLI 를 쓰며 외부 발송 API 키는 쓰지 않는다.

## 준비

1. 스크립트 위치를 잡는다(Hermes·Claude Code 공통).

   ```bash
   MC=$(ls -d "${HERMES_HOME:-$HOME/.hermes}"/skills/mail-campaign "${HERMES_HOME:-$HOME/.hermes}"/skills/*/mail-campaign \
        "$HOME"/.claude/skills/mail-campaign 2>/dev/null | head -1)/scripts/mail_campaign.py
   python3 "$MC" --version
   ```

2. gws CLI 가 있어야 한다: `command -v gws || npm i -g @googleworkspace/cli`.
3. 인증은 새로 만들지 않는다.
   - **Hermes**: google-workspace 스킬로 Google 을 이미 연결했다면(`google_token.json`) 스크립트가 `gws_bridge.py` 를 거쳐 그 토큰을 그대로 쓴다. 연결 전이면 google-workspace 스킬의 연결 절차를 먼저 한다.
   - **Claude Code**: 사용자가 터미널에서 `gws auth login` 을 마친 상태여야 한다.
4. `python3 "$MC" doctor` 로 실행기·보내는 계정을 확인하고 사용자에게 **어느 계정으로 보내는지** 알린다.

자세한 실행기 선택과 OAuth 범위는 `references/gws-and-hermes.md`.

## 흐름(9단계)

캠페인마다 폴더 하나를 쓴다(예: `~/mail-campaigns/2026-11-참가안내/`). 모든 명령은 `python3 "$MC" <명령> <폴더>`.

| 단계 | 명령 | 하는 일 | 멈추는 곳 |
|---|---|---|---|
| 1 열 매핑 | `init <폴더> --source <시트 URL>` → `check` | 필수 열(이메일·이름·세그먼트) 확인, 상태 열 7개를 없으면 만든다 | 필수 열이 없으면 `columns:` 매핑을 사용자와 정한다 |
| 2 문구 표 | `campaign.md` 편집 | 목적·세그먼트별 제목/본문·변수(`{{열 이름}}`) | 세그먼트마다 문구가 있어야 한다 |
| 3 행 검증 | `check` | 형식 오류·빈칸·중복·문구 없는 세그먼트·빈 변수 → `보류` + 사유 | 보류 행은 보내지 않고 보고만 한다 |
| 4 초안 | `preview` → `render` → (선택) `draft` | 첫 행 미리보기 → 세그먼트별 견본 → Gmail 임시보관함 초안 | 사용자가 문구를 확인한다 |
| 5 테스트 | `test` | 세그먼트마다 1통(기본 최대 3통)을 **보내는 계정 본인**에게 `[테스트]` 로 | 받은편지함에서 확인받는다 |
| 6 승인 | `plan` | 보낼 통수·보류 수·예상 시간·일일 상한 + **승인 토큰** | **사용자의 명시적 승인 전에는 `send` 를 부르지 않는다** |
| 7 간격 발송 | `send --confirm <토큰>` | 20~30초 무작위 간격, 일일 상한, 연속 3건 실패·한도/인증 오류 시 중단 | 광고는 21~08시 자동 정지 |
| 8 기록 | (send 가 자동) | 보낸 즉시 로컬 저널 → 시트 `발송 상태=보냄`·messageId·threadId·시각 | 재실행 시 보낸 행은 건너뛴다 |
| 9 답장 | `replies` → 분류 → `classify --file` | 보낸 스레드의 답장 수거 → 에이전트가 분류 → 시트 `답장 분류` | 후속 메일은 초안까지만 |

### 단계별 규칙

- **문구(2단계)**: 사용자가 준 목적과 시트 열만으로 쓴다. 받는 사람에 대해 시트에 없는 사실(직함·과거 대화)을 지어내지 않는다. 세그먼트 이름은 시트 값과 글자까지 같아야 한다. 형식은 `references/campaign-format.md`.
- **광고성 판별(2·3단계)**: 문구를 쓰거나 고칠 때마다 `references/korea-ad-law.md` 기준으로 판단한다. 쿠폰·할인·이벤트·신상품·안부 인사가 **한 줄이라도** 있으면 광고다. 스크립트도 강한 신호 단어가 있으면 `kind: 안내` 캠페인을 막는다(종료 코드 2). 막혔으면 ① 그 문구를 빼거나 ② `kind: 광고` 로 바꾸고 수신동의 열·발신자·수신거부 정보를 받는다. 거래 사실을 적은 것뿐이라 오탐이면 **사용자에게 확인받은 뒤에만** `ad_check_override: <사유>` 를 쓴다.
- **보류(3단계)**: 보류 행을 고쳐 달라는 요청이 아니면 시트 값을 직접 고치지 않는다. 사용자가 시트를 고치면 `check` 를 다시 돌려 보류가 풀렸는지 본다.
- **테스트(5단계)**: 테스트는 보내는 계정 본인이나 사용자가 지정한 본인 주소로만 보낸다. 실제 명단 주소로 테스트하지 않는다.
- **승인(6단계)**: `plan` 출력의 숫자(보낼 N통, 보류 M행, 세그먼트별 수, 보내는 계정)를 그대로 보여 주고 "보낼까요?" 라고 묻는다. "응", "보내", "승인" 같은 명시적 답이 있어야 한다. 이전 캠페인이나 테스트 때 받은 승인은 이번 발송의 승인이 아니다. 승인 토큰은 보낼 행과 본문 해시에 묶여 있어서 명단이나 문구가 바뀌면 무효가 된다. 바뀌었으면 `plan` 을 다시 보여 준다.
  - Hermes 의 명령 승인(approvals)은 메일 발송을 위험 동작으로 잡지 않는다. 이 게이트가 유일한 안전장치이므로 생략하지 않는다.
- **발송(7단계)**: 30통이면 10분 넘게 걸린다. 도구 시간 제한에 걸리지 않게 백그라운드로 돌리고 진행을 본다.

  ```bash
  nohup python3 "$MC" send <폴더> --confirm <토큰> >> <폴더>/.mail-campaign/send.log 2>&1 &
  tail -n 5 <폴더>/.mail-campaign/send.log ; python3 "$MC" status <폴더>
  ```

  로그는 `>>` 로 이어 쓴다(다시 실행해도 앞 실행의 오류가 남는다. 실행마다 `=== send 시작 … ===` 줄이 찍힌다). 같은 캠페인을 두 번 동시에 돌리면 잠금 때문에 두 번째가 거부된다. 일일 상한을 넘으면 `plan --limit N` 으로 나눠 보낸다.
- **오류 상태**: `오류`는 API 가 거절한 것(메일이 나가지 않음)이라 다음 `plan` 에 다시 포함된다. `확인 필요`는 결과를 모르는 실패다. 스크립트가 보낸편지함에서 먼저 찾아보고, 그래도 없을 때만 이 상태를 남긴다. 이 상태는 자동으로 다시 보내지 않는다. 사용자가 보낸편지함을 확인하고 상태 칸을 비운 뒤에만 다시 대상이 된다.
- **답장(9단계)**: `replies` 가 `.mail-campaign/replies.json` 을 만든다. 각 답장의 snippet 을 읽고 `reply_categories` 중 하나로 분류해 `[{"row": 5, "class": "확인", "note": "2명으로 변경"}]` 형식의 파일을 쓴 뒤 `classify --file` 로 기록한다. `반송`·`수신거부`는 항상 쓸 수 있다. `수신거부`로 분류하면 수신동의 칸이 `거부(날짜)` 가 되어 이후 광고 발송에서 빠진다. 본문 전체가 필요하면 `gws gmail +read --id <messageId>` 로 읽는다.
  - 후속 답장·리마인드는 `gws gmail +reply --message-id <답장 messageId> --body … --draft` 로 **초안까지만** 만든다. 보내기 전에 사용자 승인을 따로 받는다.
  - 답장에서 알게 된 **받는 사람 개별 사실**(담당자 변경, 호칭, 인원 변경)은 이 스킬이 아니라 **시트**에 쓴다(사용자 확인 후). 여러 캠페인에 두루 통하는 **일반 규칙**만 아래 「운영하며 더한 규칙」에 더한다.

## 상태 열

시트 오른쪽에 `발송 상태 · 보류 사유 · draftId · messageId · threadId · 발송 시각 · 답장 분류` 가 생긴다. 값과 의미는 `references/sheet-columns.md`. 사용자가 `발송 상태` 에 `제외` 라고 쓰면 그 행은 건너뛴다.

## 칸반 모드(선택, Hermes)

행마다 칸반 카드를 두고 review 단계 승인 뒤 발송하는 방식이다. 칸반이 없어도 이 스킬은 단독으로 돈다. 절차와 제약은 `references/kanban-mode.md`.

## 하지 않는 것

- 명시적 승인 없는 실제 발송, 실제 명단 주소로의 테스트 발송
- To·Cc 에 여러 명을 넣는 발송(서로의 주소가 드러난다). 한 사람에게 한 통씩만 보낸다
- 웹에서 모은 주소나 사용자가 직접 받지 않은 명단으로 발송
- 수신동의 없는 행에 광고 발송, 제목 중간·끝에 (광고) 표기
- 외부 발송 API 키 추가, 별도 OAuth 앱 생성

## 운영하며 더한 규칙

여러 캠페인에 두루 통하는 일반 규칙만 이 절에 한 줄씩 더한다(날짜·근거 한 줄 포함). 받는 사람 개인에 관한 사실은 여기에 쓰지 않고 시트에 쓴다. Hermes 에서는 `/refine` 으로 이 절에 반영할 수 있다. 어떤 규칙이 여기에 어울리는지는 `references/lessons-examples.md` 를 본다.
